# 应变（YingBian）产品介绍书

> 版本：2026-11-19
> 适用范围：当前仓库已实现的生成、交通、住宿、变化修复能力
> 读者：产品、开发、答辩评委、接手的同学

---

## 1. 一句话定位

**别人给用户一份攻略，应变给用户一张“能改的行程图”。**

计划不是一段文字，而是由节点和依赖关系组成的图：
每个节点有时间窗、是否室内、是否锁定、备选方案；每条边有最小通勤时间。
所以天气变了、有人晚到了、店关门了，系统能算出“改哪一处、代价是什么、要不要你确认”，而不是把整份攻略推倒重来。

核心原则：

1. **生成 = 反过来的修复**：先按偏好排一版，再用同一套约束自检，排不通就砍点或换点。
2. **地点必须真实**：模型只负责理解一句话，不负责编地点；地点全部来自高德检索。
3. **不确定就明说**：估算标“估算”，酒店没定标“待定”，必去点没排进去必须警告。
4. **改动可解释、可确认、可撤销**：先给方案预览，用户确认后才写进计划。

## 2. 用户看到的流程

### 2.1 新建行程

1. 首页点「新建行程」，底部弹出「说说你想怎么玩」。
2. 选日期：点日期卡片进入区间日历；第一次点选出发日，再点一天选返程日；也可以打开「灵活天数」，只固定出发日，天数交给文字解析；最多 7 天。
3. 可选填「住哪儿」：酒店名或区域（如「龙翔桥」「西湖边」「杭州东站」）。
4. 可选打开「少走路」：不做长距离步行，公交优先选步行最少的方案。
5. 写一句话偏好，或点示例。
6. 点「生成行程」。

### 2.2 行程页

- 按天展示节点：集合/出发、景点、吃饭、住宿。
- 每个节点之间显示交通方式、时长、步行距离、是否高德实时结果。
- 可以查天气、到了打卡、下雨/延误时出修复方案。
- 首页「我的计划」保留历史生成结果。

## 4. 生成计划：完整标准

### 4.1 输入字段与默认值

`Preferences` 的默认值：

| 字段 | 默认 | 说明 |
|---|---|---|
| city | 杭州 | 城市 |
| date | 当天 | 出发日，格式 YYYY-MM-DD |
| startTime | 09:30 | 每天开始时间 |
| endTime | 20:00 | 每天结束时间 |
| interests | 景点、公园、博物馆、咖啡 | 最多 4 个 |
| mustVisit | 空 | 最多 3 个 |
| avoid | 空 | 最多 4 个 |                                                                                                      //兴趣，必须，避免，最多可以不要设置这么低的上限吗
| pace | normal | relaxed / normal / packed |
| maxTransitMin | 45 | 单段通勤上限（分钟） |//单段上限改更久，你帮我权衡一下，是90min还是1h
| days | 1 | 1–7 天 |//上限可以提高吗
| budgetPerPerson | 0 | 0 表示不限 |
| preferHighRating | false | 是否明确要“评价好的” |// 默认评价好的
| lodging | 空 | 酒店名或区域 |
| avoidWalking | false | 少走路 |

### 4.2 一句话怎么变成偏好

两条路，优先 AI：

1. 配了 DeepSeek Key → 模型解析；否则规则解析。
2. **请求体里显式给的字段优先**：AI 只补空字段，不覆盖用户明确传的值。
3. 模型解析结果必须过校验，否则退回规则值：
   - 时间必须是合法 `HH:mm`；
   - pace 必须是三个枚举之一；
   - maxTransitMin 夹在 5–120；
   - interests 最多 4 个、mustVisit 最多 3 个、avoid 最多 4 个；
   - budgetPerPerson 在 1–10000 之外视为无效；
   - days 夹在 1–7；
   - lodging 最多 40 字；
   - avoidWalking 取 AI 与规则的“或”。

规则解析能识别的典型说法：

- 时间：「不想早起 / 睡到自然醒 / 晚点出发」→ 10:30；「早上 / 一早」→ 08:30；「中午」→ 11:30；「早点回 / 不想太晚」→ 17:30；「全天 / 一整天」→ 21:00。
- 节奏：「轻松 / 不赶 / 慢慢」→ relaxed；「紧凑 / 多去几个」→ packed。
- 必去：「必去 / 一定要去 / 必须去 / 想去」后面的地点名。
- 天数：「3天2晚」「两天」「周末（=2 天）」。
- 预算：「人均 100」「预算 200」「50 块以内」。
- 评价：「评分高 / 评价好 / 口碑好 / 高分」。
- 住宿：「住在XX」「住XX酒店/宾馆/民宿」「酒店定在XX」，去掉“附近/周边/一带/区域/边”后缀。
- 少走路：「不想多走路 / 少走路 / 不想走路 / 别走太多 / 走不动 / 腿脚不便」。

### 4.3 候选点从哪来

1. 兴趣词先翻译成能检索的关键词：
   - 景点→景点；古镇→古镇/老街；公园→公园；博物馆→博物馆；咖啡→咖啡；美食→美食；夜景→夜景；爬山→山。
   - 「拍照 / 摄影 / 打卡」是风格词，不拿去检索。
   - 一个能检索的词都没有时，退回默认四个词：景点、公园、博物馆、咖啡。
2. 每个关键词在高德按城市检索，单次最多 20 条，`citylimit=true`，`extensions=all`。
3. 同名去重。
4. 命中 `avoid` 里任何词的候选直接剔除（匹配名称 + 类型文字）。
5. 质量过滤：
   - 咖啡/餐饮：有评分且低于 4.0 → 剔除；
   - 任何类别：有评分且低于 3.6 → 剔除；
   - 咖啡/餐饮/购物：同一品牌只留一家（品牌名取括号前），评分高者胜，评分相同留人均低的；
   - 真景点和吃喝累计 ≥ 6 个时，购物/未分类点全部不要；不足 6 个时才作为补充。

> 没有评分的点不会被剔除。小城市高德经常没有 `biz_ext`，一律剔除会只剩几个点。

### 4.4 必去点

- 对每个必去名称做一次高德检索（最多 5 条），名称互相包含即算命中。
- 被 `avoid` 命中、或搜不到 → 进入 `unresolvedMustVisit`，并写警告。
- 必去点只在第 1 天排，且**不受 45 分钟通勤上限限制**（上限临时放到 1440 分钟），只受当天时间窗和营业时间限制。
- 来不及排进去 → 警告「必去点 X 来不及排进行程，已跳过」。

### 4.5 起点与住宿锚点

**起点**

- 填了 `startPlace` 且能搜到 → 用它。
- 否则用候选池所有点的地理中心造一个虚拟起点，名字为「城市市中心」。//虚拟起点到第一个目的地的通勤计算规则是什么

**住宿（已实现）**

- 只有多日行程才处理住宿；单日不生成住宿节点。
- 填了 `lodging`：
  - 用高德按名称检索，名称互相包含即命中；
  - 命中后成为每天的地理锚点：
    - 第 1 天结束：从最后一站到酒店，按真实路径算时长，到店时间 = 最后一站离开 + 通勤；
    - 第 2 天起：集合/出发节点就在酒店，09:30–09:50，第一段从酒店出发；
    - 酒店节点标题为「酒店名 · 住宿（第 N 晚）」，结束时间记为 23:59；
    - 酒店节点置信度按高德数据完整度：评分/人均/营业时间三项齐全=high，有 1 项=medium，都没有=low。
  - 搜不到 → 写警告，回退成“过夜占位”。
- 没填 `lodging`：
  - 只放“过夜占位”，时长 1 分钟，通勤为 `placeholder`、0 分钟；
  - 明确警告“住宿未指定，入住时间和酒店通勤未计入”；
  - 第二天沿用前一天最后一站作为起点，不假装从酒店出发。//给一个可以填写的模块，如果用户填入酒店名，你就计算本日最后一个地点到酒店，酒店到明天第一个地点，随时可填可跟新，如果用户未填你就不写这两段通勤时间
- 住宿节点当前**不锁定**：用户可以自己改；后续可加“锁定住宿”。

**尚未实现（明确边界）**

- 房态、房价、可订状态；
- 真实入住/退房时间约束（当前到店只作为时间点，23:59 只是当天结束）；
- 中途换酒店事件（“今晚住别处”）；
- 具体酒店推荐（没有库存接口，不编）。

### 4.6 每天怎么排点

时间和节奏：

- 每天先有 20 分钟集合/出发节点；正式排点从 `startTime + 20 分钟` 开始。
- 每天结束时间 = `endTime`（默认 20:00）。//你会根据前面的时偏好自动调整吗
- 停留时长 = 经验值 × 节奏系数，且不少于 20 分钟：
  - 经验值：景点 90、室内景点 80、餐饮 60、咖啡 40、购物 60、其他 45；//经验值的设定会影响具体的什么判断，设置依据是什么
  - 节奏系数：relaxed 1.3、normal 1.0、packed 0.75。
- 每天最多 13 个排点（`MAX_NODES = 14`，减去集合点）。

硬约束（不满足直接跳过）：

1. 这一段通勤超过 `maxTransitMin`（默认 45 分钟）。注意：排序阶段用的是直线估算，//可以用更准确的高德地图真实情况估算吗
   最终高德真实时长可能略高；真实时长只影响“当天还放不放得下”，不会回头改选点；
2. 到达 + 停留超过当天结束时间；
3. 有营业时间且到达早于开门、或离开晚于关门；
4. 预算：人均高于 `budgetPerPerson`（0 表示不限；高德没给人均时不做判断）；
5. 同类数量超上限：
   - 咖啡 2、餐饮 2、购物 1、其他 1、室内景点 3、景点 4；
   - 更粗分组：吃喝合计 3、购物 1、景点 4。

打分（分数越低越优先，起始分 = 通勤分钟）：

| 条件 | 加减分 |
|---|---|
| 通勤 ≤15 分钟 | 理由里写“顺路” |
| 同类已排 N 个 | +12 × N |
| 与上一站同类 | +60 |
| 高德评分 | −(评分 − 3.5) × 8 |
| 评分 ≥4.3 | 理由里写“评分 X” |
| 人均在预算内 | −6，理由写“人均 ¥X” |
| 购物/未分类 | +80（垫底） |
| 明确要“评价好的”但没有评分 | +25 |
| 有招牌菜/标签 | 理由里写“招牌：…” |

选择方式：每轮从剩余候选里取分数最低且满足硬约束的一个，形成“贪心最近邻”，直到排满或没有可排的点。

### 4.7 时间校准与砍点

排序阶段用直线距离估算通勤；排完后逐段调用真实交通决策（见第 5 节）：

- 到店时间 = 当前时钟 + 真实通勤；
- 有营业时间：到店早于开门就等到开门；等到关门前来不及 → 跳过这个点；
- 超过当天结束时间 → 当天到此为止；
- 必去点没排进去 → 写警告。

### 4.8 生成后的自检

两件事都做：

1. 时间校验：节点重叠、边的最小间隔不足、时长为负；
2. 引擎复核：用一个无影响的“假事件”跑一遍传播，任何节点不是 `ok` 都算问题。

自检不过时：

- 先砍掉最后 2 个节点，再检查；
- 砍完能过 → 采用砍过的版本，并警告“排得太满，已自动砍掉最后 2 个点”；
- 砍完仍不过 → 保留原计划，把具体问题原样写进警告，不假装成功。

### 4.9 产出与诚实标注

每个节点的 `confidence`：

- high：评分、人均、营业时间三项齐全；
- medium：有 1–2 项；
- low：都没有。

每条交通的 `source`：

- `amap`：高德路径规划；
- `estimate`：本地估算（地图不可用）；
- `placeholder`：住宿未定，通勤未估算。

生成结果还包含：

- `generation.warnings`：所有需要用户知道的问题；
- `generation.transportSources.amap / estimate`：这次有多少段用了真地图、多少段是估算；
- `generation.lodging`：请求的住宿、是否解析成功、解析到的名称；
- `generation.avoidWalking`：是否启用了少走路；
- `generation.humanSummary`：给用户看的一句话理解结果。

## 5. 交通方式：完整判断条件

### 5.1 数据来源

| 方式 | 高德接口 | 说明 |
|---|---|---|
| 步行 | `/v3/direction/walking` | 距离、时长 |
| 公交/地铁 | `/v3/direction/transit/integrated` | 多条方案；可挑步行最少的一条 |
| 驾车/打车 | `/v3/direction/driving` | 距离、时长 |
| 骑行 | `/v4/direction/bicycling` | 距离、时长 |

- 时长单位从秒换算成分钟；
- 公交方案会解析线路名，例如「地铁 1 号线 + 步行」；
- 公交返回多条方案时：
  - 默认取第一条；
  - 少走路模式取「步行总距离最短，其次时长最短」的一条。//和默认第一条不冲突吗
- 每段结果都带 `walkM`（这段路要步行多少米）。

### 5.2 默认偏好：公交优先

| 直线距离 | 决策 |
|---|---|
| ≤350 米 | 直接步行（短距离接驳，任何车都不划算） |
| 350–800 米 | 直接步行（“800 米内步行最直接”） |
| 800–4500 米 | 先查公交；步行 ≤2000 米且估算比公交快 ≥5 分钟才查步行；骑行估算比公交快 ≥5 分钟才查骑行；谁比公交快 ≥5 分钟就选谁，否则公交 |
| >4500 米 | 先查公交；公交 <35 分钟直接公交；≥35 分钟才查打车；打车快 ≥15 分钟或公交 ≥50 分钟 → 打车，否则公交 |

“明显更快”的门槛是 **5 分钟**：19 分钟步行不会赢 20 分钟公交。

### 5.3 少走路偏好

- 不选择纯步行段；只有 ≤350 米的短接驳不可避免。
- 公交必须选「步行总距离最短」的方案。
- 只有满足下面任一条件才查打车：
  - 公交方案下车后还要步行 ≥800 米；
  - 距离 ≥5 公里且公交 ≥40 分钟。
- 查到打车后：
  - 公交步行 ≥800 米且打车不比公交慢超过 10 分钟 → 打车；
  - 或打车比公交快 ≥10 分钟 → 打车；
  - 否则仍坐公交。

### 5.4 地图不可用时的估算

不同方式用不同速度，不能全按公交算：

| 方式 | 速度 | 固定开销 |
|---|---|---|
| 步行 | 4.2 km/h | +2 分钟 |
| 骑行 | 12 km/h | +3 分钟 |
| 驾车/打车 | 25 km/h | +5 分钟 |
| 公交/地铁 | 15 km/h | +10 分钟 |

统一按直线距离 ×1.2 作为绕行系数，最少 5 分钟；结果标 `estimate`，界面显示“估算 / 地图暂不可用”。

### 5.5 限流与失败处理

- 每次高德请求间隔 0.55 秒；
- 单次请求最多重试 3 次，退避 0.8 / 1.6 / 2.4 秒；
- 连续 3 次失败才熔断 20 秒，避免一次 QPS 抖动把整份计划都锁成估算；
- 相同起点、终点、方式、公交策略会缓存，重复路段不再请求。

### 5.6 界面展示

每段交通显示：

`方式/线路 · 距离 · 约 X 分钟 · 步行 Y 米 · 高德预估/估算`

- 高德结果用绿色；
- 估算额外提示“地图不可用，已留出保守余量”；
- 显示选择理由，例如：
  - “公交优先：步行/骑行没有明显更快”
  - “比公交快 12 分钟”
  - “少走路：已选步行最少的公交方案”
  - “少走路：公交步行太远或打车明显更快”

## 6. 行程变化：完整判断条件

### 6.1 事件类型

| 事件 | 字段 | 效果 |
|---|---|---|
| 下雨 rain | from / to / prob | 室外且时间重叠的节点标风险；概率 <0.30 直接忽略 |
| 延误 delay | nodeId / minutes | 目标节点后移，并沿依赖向后传播 |
| 取消 cancel | nodeId | 目标节点标为不可行 |
| 临时关闭 closed | nodeId | 同取消 |
| 同行人晚到 memberLate | personId / minutes | 转成该成员第一个节点的延误 |

### 6.2 四种状态

| 状态 | 含义 |
|---|---|
| ok | 正常 |
| at_risk | 有风险，但还能通过挪时间/换点解决 |
| conflict | 锁定节点遇到风险，必须问用户是否解锁 |
| invalid | 不可行：店取消/关门、或后移超过最晚时间 |

### 6.3 传播规则

- 先算直接命中；
- 锁定节点：`confirmed=true` 且只是有风险 → 升级为 `conflict`，方案阶段直接 blocked；
- 锁定节点如果已经不可行（店没了）→ 保持 invalid，允许换备选；
- 沿边传播：
  - 缓冲 = 实际间隔 − 边的最小间隔；
  - 上游后移先吃缓冲，吃不完的部分才顶到下游；
  - 下游新开始时间晚于 `windowLatest` → 该节点 invalid。

### 6.4 影响面与处理路径

| 受影响比例 | 路径 | 含义 |
|---|---|---|
| ≤30% | local | 局部调整 |
| 30%–60% | vote | 多人投票 |
| >60% | global | 整体重排/大改 |

### 6.5 两套方案

| 权重 | 保时间 A | 保体验 B |
|---|---|---|
| 后移每分钟 | 0.2 | 4 |
| 换备选 | 300 | 50 |
| 放弃 | 1500 | 1200 |
| 每个动作固定代价 | 0 | 15 |

- **保时间**：能挪就挪，几乎不换点、不删点。
- **保体验**：有室内备选就换；挪动超过约 15 分钟就宁可换；没备选时宁可挪很久也不删。

### 6.6 每个节点可选动作与代价

| 动作 | 适用 | 代价 |
|---|---|---|
| shift 后移 | 只对降雨、且节点是 at_risk；后移后不能超过 windowLatest | 分钟数 × w_shift + w_action |
| replace 换备选 | 降雨要求备选是室内；取消/关闭要求备选不是原节点 | w_replace + 备选通勤 × 0.5 + w_action |
| drop 放弃 | 锁定且 at_risk 时不允许 | w_drop + w_action |
| trim 缩短停留 | 打卡晚到场景，用缩短当前停留吸收延迟 | 由打卡流程单独生成 |

每个候选动作都会**试算**：改完后重新传播，如果产生新的 blocked 就丢弃。最后选代价最低且能通过试算的动作。

### 6.7 轮次与结果

- 最多修 3 轮；
- 每轮处理所有非 ok 节点；
- 结果状态：
  - ok：全部节点恢复正常；
  - partial：还有节点处于风险；
  - blocked：锁定冲突、或没有任何不牵连其他节点的改法，需要用户决定；
- 保留率 keepRate = 锁定节点中开始/结束时间没变的占比；
- 每次结果都带 actions、sacrifice、changedCount、elapsedMs。

### 6.8 应用与撤销

- 方案只是预览，用户点确认后才 `apply` 写入；
- 每次应用前保存版本，支持 undo 回上一版；
- 同一个计划可以反复改，版本号递增。

## 7. 天气与定位

### 7.1 天气

- 优先和风天气：取未来 2 小时逐小时降水概率的最大值；
- 和风不可用 → 高德当日预报文字：
  - 含“雨” → 0.8；
  - 雪/雷 → 0.7；
  - 阴/云/雾 → 0.3；
  - 其他 → 0.1；
- 两者都没有 → 演示值 0.7，并标明原因。

### 7.2 定位

- 只做“主动打卡/一次性定位”，不共享持续轨迹；
- 根据当前位置与下一站的距离、当前时间判断是否落后；
- 晚到方案要用户确认后才改行程。

## 8. 多人协作（简要）

- 成员加入是幂等的；
- 投票用于影响面 30%–60% 的场景；
- 只同步“晚到/投票”这类状态，不发送成员位置轨迹；
- 个人计划可以从共同计划派生，互不覆盖。

## 9. 失败与降级策略

| 情况 | 行为 |
|---|---|
| 没有 AMAP_KEY | 生成直接失败，提示配置 Key |
| 高德检索失败 | 生成失败，返回可读原因 |
| 路径规划失败 | 该段退回估算，标 `estimate`，计划继续 |
| 高德 QPS 超限 | 退避重试；连续 3 次失败熔断 20 秒 |
| 必去点搜不到 | 写警告 + 标记待确认，不静默丢掉 |
| 住宿搜不到 | 写警告 + 回过夜占位 |
| 排得太满 | 自动砍最后 2 个点，写警告 |
| 锁定节点冲突 | 不自动改，弹“要解锁吗” |
| 没有任何可行改法 | 返回 blocked，交给用户决定 |

## 10. 已知限制与下一步

### 当前限制

1. 停留时长是经验值，不是每家店的实际建议游览时间。
2. 打车只算时间，不算车费，也没有和人均预算联动。
3. 骑行不检查共享单车是否有车。
4. 公交方案不感知实时班次和等待时间，只使用高德返回的时长。
5. 住宿没有房态、房价、可订状态；只做地理锚点。
6. 中途换酒店还不是一个正式事件。
7. 地点质量依赖高德数据覆盖；没有评分的点会保留，可能混入低质地点。
8. 通勤上限和“步行 800 米 / 2000 米”等距离阈值用的是直线距离；实际道路距离会更长。

### 建议的下一步

1. 住宿：支持“换酒店”事件，只重排当天尾段和第二天早上。
2. 交通：把打车费用纳入预算约束；接入共享单车可用性。
3. 选点：加入“营业状态/临时关闭”的实时校验。
4. 多人：在生成阶段就支持多人偏好合并，而不只是事后投票。
5. 学习：记录用户实际停留时长，逐步替换经验值。

## 11. 验收清单

生成：

- [ ] 单日行程没有住宿节点。
- [ ] 多日 + 填住宿：第 1 天有酒店节点，第 2 天出发节点在酒店。

- [ ] 住宿名搜不到：有明确警告。
- [ ] 必去点搜不到/排不进：有明确警告。

交通：

- [ ] ≤800 米默认步行。
- [ ] 800–4500 米：步行/骑行只明显更快（≥5 分钟）才取代公交。
- [ ] >4500 米：公交 <35 分钟不叫车。

- [ ] 高德失败时标“估算”，不伪装成真实结果。
- [ ] 每段显示方式、时长、步行距离、来源。

变化：

- [ ] 降雨概率 <0.30 不影响计划。
- [ ] 锁定节点遇到风险会 blocked，不自动改。
- [ ] 保时间/保体验给出的动作不同，且理由可解释。
- [ ] 应用前可预览，应用后可撤销。

## 13. 设计取舍说明（给评委/接手同学）

1. **为什么不让模型挑地点**：模型会编不存在的店；高德能给出真实坐标、评分、人均、营业时间，且可复核。
2. **为什么用贪心而不是全局最优**：生成要快、要可解释；每一步为什么选它都能说清楚。全局最优可以以后再加，但不能牺牲可解释性。
3. **为什么保留“估算”**：演示现场网络不稳定，宁可给保守估算并明说，也不要让整个产品卡死或伪装成实时数据。
4. **为什么住宿先做锚点**：住宿位置对路线影响最大，但酒店库存对接成本高；先把“住哪儿”变成真实约束，收益最大、风险最小。
5. **为什么锁定优先**：用户明确确认过的东西不能被系统偷偷改；宁可停下来问一句。
