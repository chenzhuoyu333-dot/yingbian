## 2. P1：发布前应处理

### P1-1 “提醒/待办合并”只完成了一半，旧页面成了死代码

**现象**

- 底部导航现在是 4 个：计划、行程、提醒、我的。
- `AppScreen.Scheme`、`AppScreen.Todo`、`SchemeScreen()`、`TodoScreen()`、`confirmNotifications()`、`toggleNotification()`、`buildTodos()` 仍在代码里，但主流程没有入口调用它们。
- 第 12 项需求写的是“通知和待办合并成一条行动项”；当前实际做法是：应用方案后生成 `notifications`，然后跳到“提醒”页。旧 `TodoScreen` 不再可达。

**影响**

- 用户看到“提醒”页时，里面主要是通知，不是完整的“通知 + 待办”合并模型。
- 维护者会误以为待办仍然存在，后续改需求容易改错页面。
- `PlanController.kt` 里有 400 行左右的死代码，增加编译和排查成本。

**建议改法**

1. 确定唯一模型：一条变化 = 一条行动项，字段包含 `kind=auto/assist/info`、是否完成、按钮动作。
2. 把 `NotificationRow` 和 `TodoRow` 合成一个 `ActionItem`；提醒页直接展示。
3. 删除 `SchemeScreen`/`TodoScreen`/`confirmNotifications`/`buildTodos`，或把它们显式标为“仅调试、不接入”。

**验证方式**

- 应用一次方案后，提醒页只出现一条完整行动项，不再出现第二个待办页。
- 用 `rg "TodoScreen|confirmNotifications|AppScreen.Todo"` 应只找到定义处，不应有可达入口。

### P1-2 LAN 包的默认后端 IP 是旧地址

**现象**

`android/app/build.gradle.kts` 的 `lan` flavor 默认值是：

```text
http://10.195.151.83:8000
```

本次机器实际地址是：

```text
http://10.195.115.203:8000
```

**影响**

- 如果在没有传 `-PbaseUrl` 的情况下直接打 LAN 包，App 首屏会连不上。
- 自动寻找和 App 内连接设置可以补救，但会让第一次打开多一次失败。

**建议改法**

- 发布包统一用 `-PbaseUrl=http://当前电脑IP:8000` 打包。
- 或者把默认值改成当前开发机 IP，并在演示前用 `ipconfig` 确认。
- 长期方案是让 App 默认先走自动发现，再回退到手动地址。

**验证方式**

- 手机和电脑同一 Wi-Fi，安装后直接打开，首页能拿到 `/api/plans`。
- 浏览器打开 `http://当前IP:8000/api/plans` 能看到 JSON。

### P1-3 版本号从未升级

**现象**

`versionCode = 1`、`versionName = "1.0"` 从首次交付保持到现在。

**影响**

- 多次覆盖安装时，系统无法区分新旧版本。
- 出现签名冲突或回退时，排查会误判“是不是同一个版本”。
- 后续验收和发版记录无法对应。

**建议改法**

- 每次交付至少把 `versionCode` 加 1；`versionName` 改成 `1.1`、`1.2` 这样的可读版本。
- 本次发布建议 `versionCode=2`、`versionName="1.1"`。

**验证方式**

- `adb shell dumpsys package com.example.yingbian | rg version` 能看到新版本号。
- 旧版覆盖安装时能正常识别为升级。

### P1-4 酒店“到达时间”超过 23:59 时会被压成 23:58

**现象**

`yingbian/generate.py` 中，用户指定了住宿时：

```text
hotel_start = 最后一站离开 + 高德酒店通勤
if hotel_start >= 23:59: hotel_start = 23:58
```

这不是“到达时间”，而是为了满足当天表格式而强行截断。

**影响**

- 如果最后一站很晚，界面会显示一个假的 23:58 到店时间，用户会以为真的赶得上。
- 第二天的出发时间仍默认 09:30，没有说明“昨晚到店可能已过午夜”。
- 这是“数据看起来完整、但实际上不真实”的典型问题，和产品原则冲突。

**建议改法**

- 不要静默截断。保留真实分钟数，并在 `generation.warnings` 里写“预计到达超过 23:59，请确认是否调整最后一站或住宿”。
- 界面显示“预计次日 00:xx 到达（超出当天时间轴）”，不要伪装成 23:58。

**验证方式**

- 生成一份 23:00 后还排了夜景点且住宿在远处的多日计划。
- 检查节点时间是否不再被无提示改成 23:58，警告中是否出现明确提示。

### P1-5 天气只取“第一个有坐标的节点”，不是按当天/当前位置覆盖

**现象**

`/api/plan/{plan_id}/weather` 和巡检 `_check_weather()` 都取第一个有坐标的节点作为天气查询点。

**影响**

- 同一城市单日行程通常没问题。
- 多日、跨区或酒店离景点很远时，用户看到的是“第一个景点”的天气，不是当天行程所在地或当前位置。
- 天气提醒可能对后面的户外点误报或漏报。

**建议改法**

- 按日期分组，每天取当天第一个/最具代表性的户外点；或优先使用用户当前定位。
- 返回结构里增加 `scope`（当天、当前位置、整份计划）和 `coveredDates`，界面如实展示。

**验证方式**

- 用一份跨两个区的两天计划，让两天的天气接口结果不同；确认提醒分别对应各自日期。

## 3. P2：会造成误判或增加长期成本

### P2-1 主动定位只在 App 前台运行

**现象**

`App.kt` 的自动定位循环每 60 秒执行一次，但前提是 App 在前台、有定位权限、当前有行程。App 被切到后台或进程被系统回收后不会继续巡检。

**影响**

- 用户关闭 App 后不会收到“你落后了/天气影响了行程”的主动提醒。
- 对外宣传“主动感知”时，必须限定为“打开 App 时主动检查”，不能暗示后台持续监控。

**建议改法**

- 短期：在界面和介绍书明确“仅前台巡检”。
- 长期：使用 WorkManager/前台服务做低频检查，且必须给用户开关和隐私说明。

### P2-2 历史行程只能逐条删除，没有“清空全部”

**现象**

本次是通过文件系统把 `data/plans/` 移空；App 里只有每条行程的“删除”按钮。

**影响**

- 演示前清理历史要人工操作，容易漏。
- 用户无法在 App 内一键恢复干净状态。

**建议改法**

- 在“我的计划”增加“清空我的历史”，只删 `builtin=false`，保留内置示例。
- 后端增加 `DELETE /api/plans?scope=mine` 或等价接口，并写操作日志。

### P2-3 所有接口 CORS 全开、明文 HTTP 全开

**现象**

- `server/app.py` 使用 `allow_origins=["*"]`。
- `AndroidManifest.xml` 使用 `usesCleartextTraffic="true"`。

**影响**

- 局域网演示方便，但公网部署会扩大攻击面。
- 明文 HTTP 不适合携带真实账号、支付或隐私数据。

**建议改法**

- 演示版可以保留，但 README 和介绍书明确“仅局域网演示”。
- 公网版改为 HTTPS + 白名单来源，并关闭全局 cleartext。

### P2-4 单文件过大，后续修改冲突概率高

**现象**

- `server/app.py` 约 1175 行。
- `android/.../ui/Screens.kt` 约 2470 行。
- `yingbian/generate.py` 约 1036 行。

**影响**

- 两个队友同时改界面或接口时容易冲突。
- 责任边界不清晰，测试也很难按模块组织。

**建议改法**

- 后端按 `routes/plan.py`、`routes/generate.py`、`routes/collab.py` 拆。
- Android 按 `PlanScreen`、`ReminderScreen`、`ProfileScreen` 拆文件。
- 生成器拆成 `candidate_pool.py`、`scheduler.py`、`validator.py`。

### P2-5 高德检索缓存没有过期策略

**现象**

`yingbian/poi.py` 的 `_CACHE` 是进程内字典，按“城市 + 关键词 + 数量”缓存，但不会过期。

**影响**

- 长时间运行后内存会慢慢增长。
- 高德地点信息更新、Key 更换或城市数据修正后，旧结果会一直用到重启。

**建议改法**

- 给缓存加 TTL（例如 30 分钟）和最大条数。
- 提供一个 `refresh=true` 参数或管理接口用于演示前刷新。

### P2-6 协作/投票状态只在内存，重启即清空

**现象**

`yingbian/collab.py` 的 `CollabState` 是单进程内存状态；注释也说明重启会清空。

**影响**

- 多人演示时后端重启，成员、投票和活动流都会消失。
- 不能支撑真正的多设备长期协作。

**建议改法**

- 至少把成员、投票、活动流写入 `data/collab/<plan_id>.json`。
- 多进程部署时换成 Redis/SQLite，避免每个 worker 各有一份状态。

### P2-7 交通方式阈值使用直线距离，和真实道路有偏差

**现象**

`choose_route()` 先用坐标直线距离判断“800 米内步行、4500 米内公交、长途打车”，只有最终边才走高德路径。

**影响**

- 跨江、绕路、景区内部道路会让“直线很近”实际很远。
- 第一次粗排可能选错方式，虽然最后会用真实时长校正，但用户看到的解释可能不够准确。

**建议改法**

- 保持“粗排用直线、最终用高德”的性能取舍，但在界面明确标“通勤为地图预估”。
- 对阈值附近的边，增加一次真实路线比较。

### P2-8 必去点默认只排第 1 天

**现象**

`generate.py` 只在 `day == 1` 时把 `must_pois` 放进当天的选择池；多日行程后面的天不会继续安排没排完的必去点。

**影响**

- 用户写了多个必去点，第一天时间不够时，后面的天也不会补排，只会在第一天结束时给“来不及排进”的警告。

**建议改法**

- 把 `must_pois` 按天消费：每天先排当天的必去点，排不完的进入下一天。
- 在 `generation` 里记录每个必去点最终落在哪一天。

### P2-9 跨天营业/夜间营业地点的时间窗不校验

**现象**

`Poi.open_window()` 遇到 `17:00-02:00` 这类跨天营业时间会直接返回 `None`，等于“没有营业时间约束”。

**影响**

- 夜景点、酒吧、夜市可能被排到任意时间。
- 系统不会提示“这个时间可能没开门”。

**建议改法**

- 规范化营业时间：结束时间小于开始时间时，视为跨天，并按日期展开。

### P2-10 所有节点时间都是 `HH:mm`，没有跨日表示

**现象**

- `parse_time()` 只处理 `HH:mm`，`format_time()` 对超过 23:59 的分钟数会输出 `24:xx`。
- 酒店、夜间行程、总体延误都可能越过午夜。

**影响**

- 跨午夜计划的时间比较和显示不稳定。
- 和“真实到达时间”有关的承诺容易失真。

**建议改法**

- 内部统一用“日期 + 分钟”或 ISO 时间；展示层再转成用户时区。
- 这是结构性改造，建议在“跨日行程”需求确定后做。

## 4. P3：工程卫生和文档

### P3-1 根目录直接跑 pytest 会被缓存目录权限卡住

**现象**

根目录存在多个 `pytest-cache-files-*`，直接 `pytest` 可能因为权限/锁失败。当前可复现命令是：

```text
python -m pytest tests -q -p no:cacheprovider
```

**建议**

- 在根目录 `.gitignore`/清理脚本里处理缓存目录。
- CI 和 README 统一使用同一条命令。

### P3-2 CI 用 unittest，本地用 pytest

**现象**

`.github/workflows/ci.yml` 使用 `unittest discover`，README 和本地习惯使用 pytest。

**影响**

- 两套入口对 fixture、收集顺序、失败信息的处理不同。
- 可能出现“本地过了、CI 不过”或反过来。

**建议**

- 统一用一个入口，并让 CI 明确安装 `requirements.txt` 的所有运行依赖。

### P3-3 旧文档里的数字和代码已经不一致

**现象**

- 旧 `docs/产品介绍书.md` 里仍有“最多 7 天”“interests 最多 4 个”“mustVisit 最多 3 个”“maxTransitMin 45”等旧口径。
- 当前代码实际是：天数上限 14，兴趣词最多 6，必去点不再截断，避免最多 8，默认通勤上限 60。

**处理**

- 不覆盖旧文档（里面有用户手写批注）。
- 新增 `docs/功能介绍书_最新版.md` 作为当前实现口径；旧文档中的批注保留作为决策历史。

### P3-4 巡检模块顶部注释仍写“空档提醒”

**现象**

`yingbian/patrol.py` 顶部仍列了“空档/没有缓冲”，但 `_check_tight` 已经删除，相关测试也要求不再出现该提醒。

**建议**

- 更新注释，避免后续维护者按旧逻辑恢复。

### P3-5 日志和测试缓存目录比较多

**现象**

根目录有多份 `server*.log` 和 `pytest-cache-files-*`。它们多数被 `.gitignore` 排除，但会让目录看起来很乱。

**建议**

- 保留最近一份运行日志即可，定期清理；不要提交日志。

## 6. 建议的修复顺序

1. **先修 P1-1、P1-2、P1-3**：让“最新版”的入口、连接和版本号可信。
2. **再修 P1-4、P1-5**：不要让酒店时间和天气范围产生错误承诺。
3. **然后做 P2-1、P2-2**：把“主动感知”和“历史清理”的边界讲清楚。
4. **最后做 P2-3 到 P2-10**：安全、拆分、缓存、跨日等结构性改进。

## 7. 本次体检没有做的事

- 没有删除用户旧文档中的手写批注。
- 没有把 `.env` 或任何 API Key 写入 Git。
- 没有在未确认的情况下重写跨日模型或多人协作存储。
- 没有把“历史行程”重新导入；清除操作有备份，可恢复。
