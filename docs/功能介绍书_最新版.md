## 1. 一句话定位

**别人给用户一份攻略，应变给用户一张能改的行程图。**

这份行程不是一段不可执行的小作文，而是一张图：

- 每个地点有开始/结束时间、是否室内、是否锁定、备选地点；
- 每两个地点之间有一条“至少需要多少分钟”的通勤边；
- 天气、迟到、地点取消发生变化时，系统先算影响面，再给两套可比较的改法；
- 用户确认后才写回行程，应用后还能撤销。

核心原则：

1. **生成 = 反过来的修复**：先排一版，再用同一套时间/通勤/锁定约束自检，排不通就换点或截断。
2. **地点必须真实**：地点来自高德 POI 检索，模型不负责编地点。
3. **不确定就明说**：估算标“估算”，酒店没定标“待定”，必去点没排进去必须警告。
4. **决策可解释**：为什么选这个点、为什么改这一站、保留了什么，都能从规则和数据里回答。
5. **只做“理解”和“解释”用模型**：大模型不直接决定改哪几站。

## 2. 用户实际看到的四个页面

当前底部导航是 4 个：

| 页面 | 作用 |
|---|---|
| 计划 | “我的计划”列表：自己的历史行程 + 内置示例；可打开、删除、新建 |

## 3. 新建一份行程：完整流程

### 3.1 输入

新建页当前支持：

- 城市：可以从省市清单选择，也可以手输；
- 日期：区间日历，点出发日再点结束日；只点出发日也算单日；
- 一句话偏好：例如“想拍照、少走路、别爬山、住杭州东站”；
- 出发点：可填地点名，也可用当前定位；
- 住宿：酒店名或附近地标；
- 节奏：轻松 / 正常 / 紧凑；
- 通勤上限：常见 45 / 60 / 90 分钟；
- 少走路开关；
- 生成按钮。

### 3.2 一句话怎么变成结构化偏好

调用链：

```text
用户一句话
  → POST /api/generate（或 /api/interpret）
  → ai.parse_preferences()
  → 优先 DeepSeek；失败/无 Key 退回规则解析
  → 校验字段
  → 生成器
```

当前 `.env` 配置项：

```text
LLM_API_KEY=真实 Key
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL=deepseek-chat
```

当前实际状态：DeepSeek 已接通，偏好解析返回 `source=ai`。如果 Key 失效、网络超时、模型返回非 JSON 或字段非法，自动退回 `source=rule`，界面仍可生成，只是解释能力下降。

模型能补的字段包括：

- 时间：不想早起 → 10:30；早点回 → 17:30；
- 节奏：轻松/紧凑；
- 兴趣：景点、博物馆、咖啡、美食等；
- 必去点；
- 避免项；
- 预算；
- 天数；
- 住宿；
- 少走路。

显式传入的字段优先于模型；模型输出必须过校验，非法时间/非法枚举/超范围数值会被规则值顶掉。

### 3.3 为什么不让模型直接生成整份计划

因为“改哪几站、保留率多少、为什么不动锁定节点”必须可复现。模型可以理解“我想轻松一点”，但不能保证：

- 地点真实存在；
- 营业时间正确；
- 两站之间真的来得及；
- 锁定节点不会被偷偷改掉。

所以模型只站两头：**理解意图**、**解释结果**；中间决策用确定性算法。

## 4. 生成计划：地点从哪里来、怎么挑

### 4.1 候选池

生成器首先检查 `AMAP_KEY`；没有 Key 直接报错，不生成假地点。

检索词由三部分组成：

```text
城市基础观光词（景点、名胜古迹、公园、博物馆）
+ 城市必看词（5A景区、风景名胜）
+ 用户兴趣词
```

每个词默认取 20 条；3 天以上逐步增加到高德单页上限 25 条。

候选池会做质量过滤：

- 用户没有明确提咖啡/下午茶/茶馆/甜品/饮品时，不排咖啡馆；
- 同品牌只留评分最高的一家；
- 有评分但低于 4.0 的吃喝类剔除；
- 有评分但低于 3.6 的任何类别剔除；
- 没有评分的点不直接判死（小城市/公园常常没数据）；
- 商场店铺、无法分类的点排到最后，只有其他点不够才补位。

### 4.2 必去点

- 用户点名的必去点用高德按名称检索；
- 搜到时自动锁定（`confirmed=true`）；
- 不受普通通勤上限过滤；
- 搜不到、被排除词挡掉、或当天时间不够时，写入未解决列表和警告，不静默消失。

当前限制：多日行程里必去点默认只在第 1 天尝试排；第一天排不完的不会自动顺延到第 2 天。这是体检报告中的 P2-8。

### 4.3 城市必看

系统额外检索“5A景区”“风景名胜”，把命中的观光点标为“城市必看”；高评分博物馆类地标也会进入这个池。

规则：

- 每天至少优先排 2 个城市必看点；
- 每天最多 3 个，之后让位给用户偏好；
- 必看点因为距离/营业时间排不进来时，退回普通候选，保证计划不会因此为空。

这解决的是“用户说想喝咖啡，结果整份计划只有咖啡馆”的问题：偏好是在城市基本盘上做加减，不是把基本盘删掉。

### 4.4 选点评分

每个候选点的分数由这些因素合成，分数越低越优先：

| 因素 | 规则 |
|---|---|
| 通勤 | 直线距离估算的分钟数直接进入分数；15 分钟内加“顺路”理由 |
| 城市必看 | 减 45 分，优先入选 |
| 同类数量 | 每多一个同类加 12 分；同类达到上限直接不允许 |
| 连续同类 | 上一站同类再加 60 分，避免连着排四个馆 |
| 评分 | 有评分时按 `(评分 - 3.5) × 8` 减分 |
| 预算 | 超预算直接不允许；在预算内减 6 分 |
| 商场/未分类 | 加 80 分，垫底 |
| 无评分 | 轻加 5 分，不硬排除 |
| 招牌标签 | 有标签会写进选择理由 |

数量上限：

- 咖啡每天最多 2 个；
- 餐饮每天最多 2 个；
- 购物每天最多 1 个；
- 室内景点每天最多 3 个；
- 室外景点每天最多 4 个；
- 吃喝合并最多 3 个。

### 4.5 每天怎么排

- 每天 09:30 默认开始，20:00 默认结束；
- 第一站前有 20 分钟集合时间；
- 每天独立一条链，天与天之间不连边；
- 每个节点都带 `date`，界面按天分组；
- 单份计划最多约 14 个节点；
- 停留时长是经验值：景点 90 分钟、室内景点 80 分钟、餐饮 60 分钟、咖啡 40 分钟、购物 60 分钟、其他 45 分钟；
- 轻松节奏 ×1.3，正常 ×1.0，紧凑 ×0.75；
- 营业时间缺失时不硬拦，有营业时间时要求“到达不早于开门、离开不晚于关门”。

### 4.6 起点和住宿

**起点优先级：**

1. 用户给的坐标；
2. 用户给的地点名（高德检索）；
3. 用户候选点的地理中心（叫“出发点”，不谎称市中心）。

如果用户选的起点离目标城市超过约 80 公里，系统按市区默认出发点排，并明确提示“跨城交通请单独安排”。

如果起点离市区远，第一段通勤会单独放宽：按最近 3 个候选点的通勤时间，取第三个再 +10 分钟，最高 120 分钟；后续各段仍按用户设置的上限。这样不会因为“出发点在郊区”直接生成失败。

**住宿：**

- 多日行程填了酒店/区域时，高德检索成真实锚点；
- 第 1 天最后一站 → 酒店，用真实路径算到店时间；
- 第 2 天从酒店出发；
- 单日行程不生成酒店节点；
- 不填住宿时只放过夜占位，不编入住时长和酒店通勤；
- 住宿搜不到时明确警告，退回占位。

当前限制：如果到店时间超过 23:59，代码会截成 23:58，这是不真实的，体检报告列为 P1-4；住宿没有房价、房态、可订状态，也不支持“中途换酒店”事件。

## 5. 交通方式：完整判断条件

### 5.1 数据来源

- 粗排：用坐标直线距离估算，速度快，不需要给每个候选点调接口；
- 最终：只对真正排进行程的边调用高德路径规划；
- 高德返回真实时长/距离/公交线路名时，`transport.source=amap`；
- 高德失败、没有 Key、限流熔断时，退回本地估算，`transport.source=estimate`，界面必须标“估算”。

### 5.2 默认策略：公交优先

`choose_route()` 的实际规则：

| 距离/条件 | 选择 |
|---|---|
| ≤350 米 | 直接步行（同栋楼/隔壁） |
| ≤800 米 | 步行 |
| 800–4500 米 | 先查公交；步行/骑行必须比公交至少快 5 分钟才替换 |
| >4500 米 | 公交 <35 分钟就不打车；公交 ≥35 分钟时，打车能省 ≥15 分钟或公交 ≥50 分钟才打车 |

### 5.3 少走路

打开“少走路”后：

- 不做长距离纯步行段；
- 公交方案选择“总步行距离最少”的那一版；
- 只有下车后步行 ≥800 米，或公交确实太慢时，才比较打车；
- 打车能省 ≥10 分钟，或公交下车步行 ≥800 米且打车不比公交慢超过 10 分钟，才选打车。

### 5.4 高德失败和限流

- 单次网络异常：当前段退回估算，不影响整份计划；
- 连续 3 次失败：熔断 20 秒，期间所有段直接用估算；
- 高德 QPS 超限（10021）：退避重试；
- 公交多方案：默认选择“总时长最短 → 换乘最少 → 步行最少”的一条，不再盲取第一条。

### 5.5 界面展示

每段交通应展示：

- 方式：步行 / 骑行 / 公交地铁 / 驾车打车；
- 预计分钟；
- 距离；
- 公交线路名或“公交/地铁”；
- 步行距离；
- 来源是“高德”还是“估算”；
- 选择理由，例如“公交优先：步行/骑行没有明显更快”。

## 6. 天气和定位

### 6.1 天气三级降级

```text
和风天气（有逐小时降水概率）
  ↓ 失败/未配置
高德天气（用天气文字做保守估计）
  ↓ 失败/未配置
演示数据（明确标 isDemo=true）
```

和风需要专属 Host：

```text
QWEATHER_HOST=xxxxxx.re.qweatherapi.com
QWEATHER_KEY=真实 Key
```

高德天气使用 `AMAP_KEY`，先逆地理编码拿 adcode，再查当日预报。高德没有降水概率，系统按文字保守映射：

- 含雨 → 0.8；
- 雪/雷 → 0.7；
- 阴/云/雾 → 0.3；
- 其他 → 0.1。

行程天气接口是 `/api/plan/{plan_id}/weather`：

- 有坐标：返回真实天气或明确标注的演示数据；
- 没有坐标的内置示范计划：返回 `available=false`，不拿默认城市天气冒充。

### 6.2 定位检查

定位是“按需读取一次”，不做后台轨迹记录：

- 用户点“定位检查”时，系统向手机要一次当前位置；
- 后端用当前位置和当前时间判断：在计划节点附近、仍在上一站、离得太远；
- 准时到点：提示打卡；
- 落后：返回落后分钟数和两套改法；
- 偏离太远：提示无法判断，不硬改行程。

App 前台每分钟自动检查一次，但 App 退到后台或被杀掉后不会继续巡检。这是当前边界，介绍和答辩时不能宣称“后台持续监控”。

### 6.3 自动提醒

巡检检查：

- 是否落后（需要位置）；
- 下一站是否快赶不上最晚进入时间；
- 行程地点降雨概率是否 ≥0.6，且后面有户外点。

“全程没有缓冲”的提醒已按产品要求删除，因为它对用户没有行动价值。

## 7. 变化发生以后：两套方案怎么来

### 7.1 事件

当前支持：

- 降雨：`{"type":"rain","from":"16:00","to":"18:00","prob":0.8}`；
- 延误：`{"type":"delay","nodeId":"n_1","minutes":30}`；
- 取消：`{"type":"cancel","nodeId":"n_2"}`。

### 7.2 传播

`propagate.py` 判断每个节点：

| 状态 | 含义 |
|---|---|
| `ok` | 不受影响 |
| `at_risk` | 受影响但还能走 |
| `invalid` | 已经不可执行 |
| `conflict` | 与锁定/依赖冲突 |

影响会沿通勤边向后传播；有缓冲时先消耗缓冲，没有缓冲才继续顶到下一站。

### 7.3 两套策略

| 方案 | 名字 | 代价权重 | 适合 |
|---|---|---|---|
| A | 保时间 | 后移很便宜，换点/删点极贵 | 时间可以让，内容尽量不换 |
| B | 保体验 | 换点便宜，后移较贵，删点很贵 | 内容尽量保留，愿意换附近地点 |

每个节点可选动作：

- `shift`：整体后移；
- `replace`：换备选；
- `trim`：缩短当前停留（用户晚到时）；
- `drop`：放弃；
- `shift_all`：同一天多次同样分钟数的后移合并成一条“整体推迟”。

如果两套方案最终计划完全一样，服务端会去重，只保留一套并标“两种偏好结果一致”，不假装有两套。

### 7.4 锁定节点

用户确认过的节点不会被自动改：

- 锁定节点遇到风险 → 返回 `blocked`；
- 提示“这是你锁定的，但会受影响。要解锁吗？”；
- 用户确认后才进入改法。

### 7.5 应用和撤销

```text
事件 → 影响面 → 两套方案 → 用户选一套 → apply → 新版本
                                      ↓
                                  undo → 上一版
```

- 应用前可以预览；
- 应用后版本号 +1；
- 撤销前可以看“会退回哪一版、会恢复哪些点”；
- 用户自己生成的计划会落盘到 `data/plans/`，重启后仍在；
- 内置示例不写盘，不会混进“我的历史”。

## 8. 多人协作

当前能做的：

- 成员用 `memberId` 加入，重复加入是幂等；
- 成员列表、活动流；
- 变化影响面在 30%–60% 时发起投票；
- 投票有 TTL，全员投完提前结束；
- 平票/零票使用默认方案；
- 投票、成员、活动流目前只在内存，后端重启会清空。

当前没做的：

- 生成阶段合并多人偏好；
- 多设备长期同步；
- 个人计划从共同计划派生；
- 位置轨迹共享（这是刻意不做）。

## 9. 数据来源和“诚实标注”

| 数据 | 来源 | 缺失/失败时 |
|---|---|---|
| 地点名称/坐标/类型 | 高德 POI | 检索失败则生成失败，不编地点 |
| 评分/人均/营业时间/电话/标签 | 高德 `biz_ext` | 缺失字段写进 `poi.missing`，不补默认值 |
| 通勤方式/时长/距离 | 高德路径规划 | 退回本地估算，标 `estimate` |
| 天气 | 和风 → 高德 → 演示 | 演示数据标 `isDemo=true` |
| 停留时长 | 经验值 | 节点写 `stayBasis`，用户可改 |
| 酒店房态/房价 | 未接入 | 明确标“住宿锚点”，不承诺可订 |
| 模型解析 | DeepSeek / 规则 | 标 `source=ai/rule` |

这条“数据来源可追溯”是产品的核心差异点，也是答辩时最容易被追问的地方。

产物：

android/app/build/outputs/apk/lan/debug/app-lan-debug.apk

android\make-apks.ps1

### 10.4 手机安装

1. 手机和电脑连同一 Wi-Fi；
2. 安装 `yingbian-lan.apk`；
3. 打开 App；
4. 如果显示连接失败，点“自动寻找服务器”，或在设置里填 `http://10.195.115.203:8000`；
5. 定位权限只在用户点定位/自动巡检时使用，不记录轨迹。

## 12. 验证清单

### 生成

- [ ] 不填住宿的单日行程没有酒店节点。
- [ ] 多日 + 填住宿：每天晚上有酒店节点，第二天从酒店出发。
- [ ] 酒店到店时间 = 最后一站离开 + 真实/回退通勤，不是固定 15 分钟。
- [ ] 不填住宿时显示“过夜占位”，不编入住时长。
- [ ] 必去点搜不到/排不进时有明确警告。
- [ ] 用户没说咖啡时，计划里没有咖啡馆。
- [ ] 生成的计划节点时间不重叠，天与天不串。

### 交通

- [ ] ≤800 米默认步行。
- [ ] 800–4500 米公交优先，步行/骑行快 ≥5 分钟才替换。
- [ ] 少走路时不出现长距离纯步行段。
- [ ] 高德失败时该段标 `estimate`。
- [ ] 每段能看到方式、时长、距离、来源和选择理由。

### 天气和定位

- [ ] 和风可用时返回 `source=和风天气`、`isDemo=false`。
- [ ] 和风失败时能用高德兜底。
- [ ] 两者都失败时返回演示数据并明确标注。
- [ ] 没有坐标的内置计划返回 `available=false`，不冒充真实天气。
- [ ] 定位到计划节点附近时能提示打卡。
- [ ] 落后时返回落后分钟数和两套改法。

### 变化

- [ ] 降雨概率 <0.30 不影响计划。
- [ ] 锁定节点遇到风险返回 blocked，不自动改。
- [ ] A/B 两套方案不同，或明确说明“结果一致”。
- [ ] 应用前可预览，应用后可撤销。
- [ ] 同一天多次相同后移合并成“整体推迟”。

### 连接和版本

- [ ] 手机和电脑同一 Wi-Fi。
- [ ] 手机浏览器能打开 `http://10.195.115.203:8000/api/plans`。
- [ ] App 设置里能看到当前服务器地址。
- [ ] 新 APK 的 `versionCode` 比旧版大。

## 13. 当前已知限制

1. 停留时长是经验值，不是每家店的实际建议游览时间。
2. 打车只算时间，不算车费，也没有和人均预算联动。
3. 骑行不检查共享单车是否有车。
4. 公交不感知实时班次和等待时间，只使用高德返回的时长。
5. 住宿没有房态、房价、可订状态；只做地理锚点。
6. 中途换酒店还不是正式事件。
7. 地点质量依赖高德覆盖；没有评分的点可能混入低质地点。
8. 通勤粗排用直线距离，真实道路会更长；最终边才用高德校正。
9. 天气目前取第一个有坐标的节点，不是按天/当前位置分别取。
10. 多日行程的必去点默认只在第 1 天尝试排。
11. 主动定位只在 App 前台运行，不是后台持续监控。
12. 协作、投票、活动流只存在内存，后端重启会清空。
13. 酒店到店时间超过 23:59 时会被截成 23:58，这是已知的展示缺陷。
14. “通知 + 待办”当前仍以通知为主，旧 TodoScreen 是残留代码。

## 14. 给评委/接手同学的 6 句话

1. 地点不是模型编的，来自高德；模型只理解偏好和解释结果。
2. 生成不是写攻略，是先生成图，再用同一套约束自检。
3. 变化不是整份重排，是先算影响面，再给两套可比较的改法。
4. 锁定节点不会被偷偷改；改不了就停下来问用户。
5. 数据缺失不补假值：估算、待定、演示、缺失都会显式标注。
6. 当前版本优先保证“能解释、能演示、能回退”，不追求不可验证的全局最优。
