# 产品问题汇总与解决方案（第三轮 12 项）

> 整理日期：2026-11-23
> 对照版本：`e9af95f` + 当前工作区未提交改动
> 说明：本文只做问题归因和方案设计，**不修改软件**。每条都写清“现在实际是什么样”“为什么会这样”“建议怎么改”“改完怎么验收”。
> 第 10 条按“设置 → 自动寻找服务器地址”理解；如果你指的是“粘贴一个网址自动抓取行程”，仓库目前没有这个功能，需要单独做，详见第 10 条末尾。

## 结论先行

这 12 条不是 12 个孤立的小问题，实际是四类：

| 类别 | 包含问题 | 一句话结论 |
|---|---|---|
| 生成结果可信度 | 6、8、9 | 先保证“有景点、不乱塞咖啡、起点远也能生成”，再谈偏好微调 |
| 变化处理闭环 | 1、2、7 | 一次变化应该是一组动作、一次确认、一条待办，而不是一长串节点 |
| 主动感知 | 3、4、5 | 定位/记录/投票要能在单人演示里跑通；天气和位置要主动弹，不是等用户点 |
| 信息架构与连接 | 10、11、12 | 底部导航要收敛；历史、当前行程、提醒、我的各归其位；自动寻找要有兜底 |

建议实施顺序：

1. **P0 先修生成可信度**：9（咖啡）→ 6（起点通勤）→ 8（城市必看池）。
2. **P0 再修演示闭环**：7（删缓冲提醒）→ 1（整体推迟合并）→ 2（撤销确认）→ 3（单人定位/记录/投票）。
3. **P1 做主动感知**：4（天气自动弹窗）→ 5（到达/偏离自动判断）。
4. **P1 做信息架构**：11（历史与行程页）→ 12（方案弹窗、提醒合并、我的）。
5. **P2 做连接加固**：10（自动寻找兜底），可以和上面并行。

## 1. 方案 B 整体推迟：待办要合并，不要罗列每个景点

**你的问题**

> 方案 B 整体推迟，把推迟行程的待办合并；推迟方案里简要写“整体推迟”，而不是罗列所有景点。

**现在实际**

- 位置晚到场景的 B 方案叫“整体顺延”，但它不是一条“整体”动作，而是给每个受影响节点各生成一条 `shift`：
  - `yingbian/location.py` 的 `_scheme_actions()` 里，`shifts = [Action(...) for node in affected]`，一个节点一条。
- 影响分析和修复引擎里，普通延迟也会给每个未解决节点各生成一条 shift。
- App 的通知和待办是“一条 action → 一条通知/待办”：
  - `PlanController.buildNotifications()` 用 `scheme.actions.mapIndexed`；
  - `PlanController.buildTodos()` 同样逐条映射。
- 结果：用户看到“整体顺延 30 分钟”，下面却列了 6 个景点、6 条通知、6 条待办，像改了 6 次，实际只是一次整体后移。

**根因**

底层把“整体后移”表达成了 N 条独立动作，UI 又严格按动作条数展示。语义上缺少“组动作（group action）”。

**建议方案**

1. 新增动作类型 `shift_all`：

   ```json
   {
     "nodeId": "d1_lunch",
     "action": "shift_all",
     "payload": {
       "minutes": 30,
       "affectedIds": ["d1_lunch", "d1_museum", "d1_sunset"],
       "count": 3
     },
     "reason": "整体后移 30 分钟",
     "sacrifice": ""
   }
   ```

2. `yingbian/location.py` 的 B 方案只生成 1 条 `shift_all`；`yingbian/repair.py` 在“同一延迟、同一分钟数、连续节点”场景也折叠成 1 条。
3. `apply_actions()` 支持 `shift_all`：把 `affectedIds` 里的节点统一加 `minutes`，效果与逐条 shift 完全一致。
4. App 方案卡片只显示一行：
   - 标题：`整体顺延 30 分钟`
   - 副标题：`影响 3 个点（14:00 午餐 → 14:30）`
   - 展开后才显示具体节点，默认不展开。
5. 通知/待办合并：
   - 通知：`告知同行：整体推迟 30 分钟，后面 3 个点顺延`
   - 待办：`告知同行：今天整体晚 30 分钟，餐厅 14:30 到`
   - 不再生成“每个景点后移 30 分钟”的 N 条。
6. 兼容旧数据：App 侧如果收到连续多条同分钟数的 `shift`，也自动折叠成一行“整体推迟”。

**验收标准**

- 晚到 30 分钟、影响 5 个点时，方案页只有 1 条“整体顺延”，通知 1 条、待办 1 条。
- 点开“查看详情”能看到受影响的 5 个节点。
- 应用后每个节点确实后移 30 分钟，时间计算结果与旧逐条 shift 一致。
- 旧计划里的逐条 shift 仍能正常应用，不会报错。

**优先级**：P0（直接影响演示观感）

## 2. 撤销要弹窗，并说明“将撤回什么”

**你的问题**

> 撤退（按“撤销”理解）希望弹窗提示撤回的内容。

**现在实际**

- 顶栏只要 `version > 1` 就出现“撤销”按钮：
  - `App.kt`：`TextButton(onClick = { controller.undo() })`，点了立即撤销，没有确认。
- 后端 `/api/plan/{id}/undo` 直接 `versions.pop()`，没有返回“这次撤回了哪一版、改了什么”。
- 用户不知道自己会回到哪一版、哪些节点会恢复。

**根因**

版本栈只存了计划快照，没有存“这次改动是什么”的变更日志；前端也没有确认弹窗。

**建议方案**

1. 后端为每个版本增加变更记录：

   ```json
   {
     "version": 3,
     "at": "2026-11-23T14:20:00",
     "actor": "张队长",
     "kind": "apply",
     "schemeLabel": "保体验",
     "summary": "餐厅取消，改去室内备选；2 个点后移",
     "changedCount": 3,
     "actions": []
   }
   ```

2. 新增 `GET /api/plan/{id}/undo/preview`，返回：
   - 当前版本、将回到的版本；
   - 这次改动的摘要、改了哪几个点；
   - 是否可以撤销（版本为 1 时不可撤销）。
3. App 点“撤销”先弹窗：
   - 标题：`撤销到 v2？`
   - 正文：`将撤回 v3「保体验」的 3 处改动：餐厅取消、博物馆后移 30 分钟、晚餐改到 18:30。`
   - 按钮：`确认撤销` / `取消`
4. 撤销成功后给一条轻提示：`已回到 v2，3 处改动已恢复`。
5. 如果当前版本是别人改的，弹窗里要显示“这版是李队友在 14:20 改的”，避免误撤别人的操作。##先不要区分队友，就保持一致处理

**验收标准**

- 点“撤销”一定先出现确认弹窗，不直接改计划。
- 弹窗能说清撤回的版本号、操作者、改动数量和关键节点。
- 取消后计划不变；确认后版本号减 1，节点恢复。
- v1 时“撤销”按钮不出现或置灰。

**优先级**：P0

## 3. 单人演示里的定位、记录、投票要真正可用

**你的问题**

> 单人演示中定位、记录、投票都没做。

**现在实际**

- 行程页顶部一直显示协作条，单人时文案是“单人演示”，但“定位 / 记录 / 投票”三个按钮都在：
  - `Screens.kt` 的 `CollabBar()`。
- 定位：
  - 在线模式点“定位”会请求定位权限并调用 `/locate`，但失败只写进 `controller.error`，行程页没有明显提示；
  - 离线模式直接返回一条写死的“落后 40 分钟”演示数据。
- 记录：
  - 只有后端活动流；单人如果没有触发变化，活动流基本只有“加入行程”一条，点开像“没做”。
- 投票：
  - 在线模式依赖成员已加入该计划；`joinTrip()` 只在 App 启动时调用一次，生成新计划后没有重新加入，容易报“你还没加入这次行程”；
  - 离线模式 `startVote()` / `castVote()` 直接抛“离线模式不支持多人协作”。
- 所以不是完全没代码，而是**单人状态下三个入口都没有形成可感知的闭环**。

**根因**

1. 协作状态只在启动时绑定一次，生成/打开新计划后没有重新 `join`。
2. 单人模式没有区分“一个人也能用的功能”和“必须多人才能用的功能”。
3. 离线模式用假数据/抛错，缺少清楚的“现在能做什么”的界面状态。
4. 活动记录只有服务端事件，没有本地“生成、打卡、应用方案、撤销”的时间线。

**建议方案**

1. **重新加入计划**：每次 `createTrip()`、`createFromText()`、`openPlan()` 成功后都调用 `joinTrip()`，确保成员、投票、活动绑定到新 `planId`。
2. **单人模式明确三种状态**：
   - 定位：真实可用。请求权限 → 取当前位置 → 调 `/locate`；成功显示“你在哪、该在哪、落后多少”；失败在行程页显示可读原因（无权限 / 没信号 / 后端不可达）。
   - 记录：本地时间线 + 后端活动流合并。至少记录：生成计划、打开计划、打卡、应用方案、撤销、处理天气提醒。单人也能看到一条完整时间线。
   - 投票：`members <= 1` 时不显示“投票”，改成“只有你一人，直接选方案”；`members > 1` 才显示投票。不要给单人一个点了就报错的按钮。
3. **离线演示**：
   - 定位保留演示数据，但必须标“演示”；
   - 记录保留本地时间线；
   - 投票按钮隐藏，并说明“离线模式没有多人协作”。
4. 协作条文案按状态变化：
   - 单人：`单人行程 · 定位可用 · 记录可用`
   - 多人：`3 人同行 · 2 人已投票`
   - 离线：`离线演示 · 仅查看/打卡`

**验收标准**

- 单人新建一份行程后，点“定位”能出结果或明确错误，不是无声失败。
- 点“记录”至少能看到“生成计划 / 加入行程 / 打卡”等记录。
- 单人时不再出现“投票”按钮；多人时投票能发起、投票、显示票数。
- 离线模式三个入口不报错、不假装成功。

**优先级**：P0（答辩演示会被直接看到）

## 4. 天气检测到影响行程时，自动弹窗让用户改

**你的问题**

> 天气变化检测出来以后，判断是否影响行程；如果影响，自动弹出提示让用户改变行程。

**现在实际**

- 后端巡检 `yingbian/patrol.py` 的 `_check_weather()`：
  - 只取行程里第一个有坐标的节点；
  - 只查当前天气的 `next2hRainProb`；
  - 概率 ≥ 0.6 且存在户外未锁定节点，就给一条 `weather` 提醒。
- App 只在行程页顶部显示一条内联的“管家提醒”，不会自动弹窗：
  - `ButlerNotice` 是页面内卡片，用户不点就看不到详情。
- 巡检每 60 秒才跑一次（`pollLoop` 里 `patrolTick % 20`），生成计划后不会立刻检查。
- 没有“这场雨会不会影响某个具体户外点”的时间匹配，也没有“同一条提醒只弹一次”的去重。

**根因**

天气数据只有“未来 2 小时一个概率”，没有逐小时/逐点匹配；前端把“提醒”当展示，不当“需要决策的事件”。

**建议方案**

1. 天气适配层输出逐小时数据：
   - 和风 `/v7/weather/24h` 已有逐小时 `pop`，保留 `hourly` 数组；
   - 高德没有概率，继续用文字保守估计，但至少给“今天有雨/无雨”的时间段。
2. 巡检按节点时间匹配：
   - 对每个户外、未锁定节点，取 `node.start ~ node.end` 覆盖的小时；
   - 如果覆盖小时内最大降雨概率 ≥ 阈值（建议 0.6），标记 `affectedNodeIds`；
   - 返回 `rainFrom`、`rainTo`、`maxProb`、`affectedNodeIds`、`severity`。
3. 前端收到“新的天气影响”时自动弹窗：
   - 标题：`15:00–17:00 有雨，可能影响 2 个户外点`
   - 正文：`岳麓山、橘子洲是户外点，按现在的时间会正好赶上降雨。`
   - 按钮：`看改法` → 直接调用 repair（rain 事件 + 时间段）；`今天先这样` → 本次不再弹；`关闭`。
4. 去重与频率：
   - 用 `planId + date + rainFrom + rainTo + affectedNodeIds` 做签名；
   - 同一签名只自动弹一次；用户点“先这样”后 30 分钟内不再弹；
   - 雨停或时间窗变化后，签名变化，可以重新提醒。
5. 触发时机：
   - 生成/打开计划后立即巡检一次；
   - App 在前台时每 5 分钟巡检一次；后台不跑，省电。

**验收标准**

- 用固定天气 fixture 模拟“15:00–17:00 降雨 80%”，计划里有 15:30 的户外点 → 自动弹窗一次。
- 点“看改法”能进入方案选择，并只改受影响的节点。
- 点“今天先这样”后，同一场雨不再重复弹。
- 室内点或降雨概率低于阈值时，不弹。

**优先级**：P1（核心卖点，但依赖天气数据质量）

## 5. 位置变化：准时到就提示打卡，偏离/迟到就问是否改行程

**你的问题**

> 地点变化要求检测是否到了行程目标地点；准时到了就弹提示打卡；没有准时到、实际定位与目标定位大于一定范围，就问是否改行程。

**现在实际**

- 定位检查只有用户手动点“定位”才会跑：
  - `yingbian/location.py` 的 `locate()`；
  - 找离当前位置最近的计划节点，必须在 1500 米内；
  - 超过 1500 米直接返回 `unknown`，只显示“你离最近的点还有 X 米，先不判断”，**不会问是否改行程**。
- 准时判断：
  - 落后小于 10 分钟返回 `on_track`，但不会自动提示打卡；
  - 打卡是底部单独的“我到了”按钮，需要用户自己点。
- 没有“到达目标点附近自动提示打卡”，也没有“偏离目标点自动问改行程”。

**根因**

定位是“用户主动查询”的一次性动作，不是“前台轻量 watcher”；`locate()` 只做落后判断，没有输出“下一步动作类型”。

**建议方案**

1. 增加前台位置观察器（只在 App 打开时）：
   - 每 2–3 分钟或位置明显变化时取一次；
   - 不存轨迹、不上传历史点，只保留“当前点”用于一次判断。
2. 后端 `locate()` 返回明确的 `action`：
   - `checkin`：距离当前目标 ≤ 150 米，且现在在目标时间窗内；
   - `change`：距离“此刻本该在”的目标 > 500 米，且已落后 ≥ 10 分钟；
   - `none`：正常/无法判断。
3. 前端两种弹窗：
   - 到达：`你已到「岳麓山」，比计划早 5 分钟，打卡吗？` → `打卡` / `还没到`。
   - 偏离/迟到：`你现在离「橘子洲」还有 1.2 公里，已落后 25 分钟，要改行程吗？` → `看改法` / `继续走`。
4. 打卡后按现有 `checkin()` 逻辑：
   - 准时：记录到达，提示“已打卡”；
   - 晚到：给出 A/B 方案（缩短停留 / 整体顺延 / 跳过）。
5. 防打扰：
   - 同一个节点、同一种状态只提示一次；
   - 用户点“继续走”后 10 分钟内不再提示；
   - 室内/地铁无信号时不要误判，距离取不到就返回 `none`。

**验收标准**

- 模拟位置在目标点 100 米内、时间在窗口内 → 弹“打卡吗”。
- 模拟位置离目标 1.2 公里、时间已过 25 分钟 → 弹“要改行程吗”，并能给出方案。
- 同一节点不重复弹；点“继续走”后冷却生效。
- 无定位权限时，页面明确提示，不静默失败。

**优先级**：P1

## 6. 起点导致通勤超时：要能生成，不要直接加载不出来；起点优先

**你的问题**

> 如果出发点导致通勤超时，要有报错信息，不能直接加载不出来；同时希望通行时长不要直接限制计划生成；定了出发地点，希望以出发点优先。

**现在实际**

- `yingbian/generate.py` 的 `_pick_origin()` 已经做了一版放宽：
  - 起点到最近 3 个点超过默认上限但 ≤ 90 分钟 → 保留起点，把本次上限提高到第 3 近 +5 分钟，并写警告；
  - 超过 90 分钟 → 退回市区中心。
- 但排序阶段 `_ordered_pick()` 仍然对每个点硬性判断：
  - `if transit > prefs.max_transit_min: continue`
  - 如果可用点不足 3 个，`generate()` 会抛 `RuntimeError`，接口返回 400。
- App 端如果 400，只显示错误文案；用户感受就是“点了生成，加载不出来”。
- 必去点目前只在第 1 天排，且用 24 小时上限绕过；普通点仍受硬限制。

**根因**

“起点第一段”和“景点之间通勤”用了同一个上限；生成器把“点不够”当成失败，而不是降级输出。

**建议方案**

1. **第一段单独处理**：
   - `first_leg_limit = max(用户上限, 最近 3 个点 + 10 分钟, 90 分钟)`；
   - 只要起点能解析、且不是跨城（>80 km），**永远保留用户起点**，不再因为第一段远而换市中心。
2. **后续段仍用用户上限**：
   - 景点之间超过上限才跳过/换点；
   - 第一段长不影响后续段的约束。
3. **不因点少而 400**：
   - 如果当天只能排 1–2 个点，照常返回计划；
   - 在 `generation.warnings` 里写：`从「绿地海外滩」到市区约 52 分钟，今天只能排 2 个点；建议晚点出发或换起点`；
   - 返回 200，App 正常展示，不出现“加载不出来”。
4. **跨城/搜不到起点**：
   - 起点距城市中心 >80 km：提示“跨城交通请单独安排”，按市区中心排，但保留用户输入作为说明；
   - 起点搜不到：提示“没搜到，已按市区中心排”，并给出可点击的“换个起点”。
5. **App 错误兜底**：
   - 如果后端仍返回 0 个点，显示“这次没排出来，试试：晚点出发 / 放宽通勤 / 去掉一个必去点”，而不是空白页。

**验收标准**

- 用手机原请求（长沙、绿地海外滩、4 天）生成：返回 200，起点仍是“绿地·海外滩”，有“第一段较远”的警告，不再 400。
- 从 100 公里外出发：返回 200，有跨城提示；或明确让用户确认，而不是直接失败。
- 只能排 1 个点时也返回计划 + 警告，不抛异常。
- 后续景点之间仍遵守用户设置的通勤上限。

**优先级**：P0（手机端已经实际踩到）

## 7. 删除“今日没有缓冲”的提醒

**你的问题**

> 今日没有缓冲的提醒是什么，删掉。

- `yingbian/patrol.py` 的 `_check_tight()` 会在“所有相邻段都没有缓冲”时生成：
  - 标题：`今天全程没有缓冲`

**根因**

“缓冲”是内部调度概念，普通用户看不懂；而且生成器本来就按最紧时间排，提示“没有缓冲”几乎必然出现，属于噪声。

**建议方案**

1. 从用户可见巡检中删除 `_check_tight()` 的告警，不再返回 `kind="tight"`。
2. 保留内部 slack 计算：
   - 只用于影响分析、方案代价、调试；
   - 不在 App 文案里出现“缓冲”两个字。
3. 删除/修改对应测试和 fixture，避免测试还期待这条提醒。
4. 如果确实要保留“今天很赶”的信息，改成用户能理解的说法，并且只在“某一段真实通勤比计划多 20 分钟以上”时提示，不再说“没有缓冲”。

**验收标准**

- App 和 `/patrol` 返回里不再出现“今天全程没有缓冲”。
- 其他天气/落后/收口提醒不受影响。
- 相关测试更新后全绿。

**优先级**：P0（一条文案，改动小）

## 8. 生成行程要先覆盖城市主要景点，偏好只是在此基础上修改

**你的问题**

> 生成行程最基本要涵盖各大景点，用户偏好只是在此基础上的修改。

**现在实际**

- 候选池完全由兴趣词决定：
  - `generate()` 先 `search_interests(prefs.city, prefs.interests)`；
  - 默认兴趣是“景点、公园、博物馆”；
  - 每个关键词最多取 20 条，再做质量过滤。
- 没有“城市必看池”，也没有“每个城市至少覆盖哪几个地标”的约束。
- 必去点只在第 1 天排；多日行程中，后面的天不一定还有核心景点。
- 如果用户只说了“拍照”“轻松”，检索词可能退化，候选池更小。

**根因**

生成逻辑是“偏好驱动检索”，缺少“城市基础景点层”。偏好被当成了“选点范围”，而不是“在基础景点上做加减”。

**建议方案**

1. 增加“城市必看池”作为第一层：
   - 用高德关键词检索：`景点`、`名胜古迹`、`博物馆`、`公园`、`地标`、`5A景区`；
   - 按评分、人气/类型、是否关闭过滤，去重后取 8–12 个；
   - 按城市缓存（例如 `data/highlights/{city}.json`），避免每次生成都查。
2. 第二层才是用户偏好池：
   - 兴趣词、必去点、预算、避免项；
   - 偏好只负责“加哪些、去掉哪些、排序”，不负责“有没有基础景点”。
3. 每天配额：
   - 每天至少 2 个“城市必看”点，再排偏好点；
   - 多日行程把必看点分散到不同天，不要全塞第 1 天；
   - 必去点跨天分配，单日放不下才警告。
4. 评分与解释：
   - 每个节点记录 `selectionReason`：`城市必看` / `你提到博物馆` / `顺路` / `必去`；
   - 用户能看到“为什么选它”，也能手动换掉。
5. 没有必看数据的城市：
   - 退回当前关键词检索，并提示“这个城市没有必看池数据，按兴趣排”。

**验收标准**

- 长沙 3 天、用户不填兴趣：计划包含橘子洲、岳麓山、湖南省博物馆等核心点（以高德实际返回为准），而不是只有小公园/咖啡馆。
- 用户填“博物馆”：在必看池基础上增加博物馆，不删掉橘子洲/岳麓山。
- 用户填“避开爬山”：岳麓山可以被排除，但要有警告和替代点。
- 每个节点能看到选择理由。

**优先级**：P0（决定“像不像一份旅行计划”）

## 10. “自动扫描网址/自动寻找”坏掉了：要有兜底和可见诊断

**先确认理解**

我按“设置 → 自动寻找服务器地址”理解。当前仓库没有“粘贴一个网址自动抓取行程”的功能；如果你说的是后者，需要新增 URL 抓取 + 解析，属于新功能，不是修回归。

**现在实际**

- `ServerDiscovery.find()` 是四段式：
  1. 已知地址（300ms 探测）；
  2. UDP 广播 8001；
  3. 每块网卡 /24 扫描；
  4. 大网段 /20 扫描，但只取前 2048 个地址，并发 64，单地址 250ms。
- 可能坏掉的地方：
  - /20 只扫“网络号开始的前 2048 个”，如果电脑 IP 在预算之外，永远扫不到；
  - 校园网/热点常开 AP 隔离，UDP 广播收不到，只能靠扫；
  - 250ms 在繁忙 Wi-Fi 上偏短，后端刚启动时也容易超时；
  - 扫描是分块串行，2048 个地址最坏要十几秒；
  - 设置页“自动寻找”失败只显示“没找到 + 网段描述”，没有“最后试了哪个地址、错在哪”。
- 这不是某一个改动能完全解决的，根因是“自动发现”本身受网络环境影响。

**建议方案**

1. 恢复一条最简单的可靠路径：
   - 上次成功地址 → 当前保存地址 → 网关地址 → 本机同 /24 → 按真实掩码扫 /20（从自己 IP 附近向两边扩展，而不是只取前 2048 个）。
2. 提高探测质量：
   - 用轻量 `/api/netinfo` 代替 `/api/plans`（后者返回大 JSON）；
   - 超时 500ms，并发 128，总预算 15 秒；
   - 找到即停，显示“找到 http://x.x.x.x:8000”。
3. 增加手动兜底：
   - 设置页保留“输入电脑 IP”；
   - PC 端启动时打印二维码/地址，手机扫码直接填入；
   - 支持 `http://IP:8000` 和 `IP:8000` 两种输入。
4. 失败诊断：
   - 显示“试过：192.168.1.0/24、10.195.144.0/20；最后错误：连接超时”；
   - 提供“复制诊断信息”按钮，方便发给我排查。
5. 生成失败时自动重试一次发现：
   - 如果当前地址请求失败，后台自动 `ServerDiscovery.find()`，找到新地址后自动重发刚才的生成请求。
6. 加日志：
   - `logs/discovery.log` 记录每次扫描的网段、耗时、命中地址。

**验收标准**

- 手机和电脑同一 Wi-Fi：10 秒内找到后端。
- UDP 被禁：/24 扫描能找到。
- 手机在 10.195.159.x、电脑在 10.195.146.x：/20 扫描能找到（不再只扫前 2048）。
- 找不到时，界面能说清试过哪些网段和最后错误，不是一句“没找到”。
- 扫码/手输 IP 一定能连上。

**优先级**：P2（影响演示稳定性，但可用手输 IP 兜底）

## 12. 方案改弹窗；通知和待办合并；新增“我的”页

**你的问题**

> 将方案改成弹窗，在需要修改时弹出；将通知和待办整合到一个页面，管理好先后顺序；加一个“我的”页面，存储用户设置、用户名等基本信息。

**现在实际**

- “方案”是底部导航的一个独立页面（`AppScreen.Scheme`），不是弹窗；
- “通知”和“待办”也是两个独立页面（`AppScreen.Notify` / `AppScreen.Todo`）；
- 设置是顶栏右上角的对话框，没有“我的”页；
- 通知和待办都按 action 顺序排，没有统一的优先级；
- 方案页、通知页、待办页各占一个底部 tab，导航很挤。

**根因**

信息架构是“按功能模块分页”，不是“按用户任务分页”。用户真正关心的是：现在要不要改、今天要做什么、我是谁/怎么设置。

**建议方案**

### 12.1 底部导航收敛为 4 个

建议：

| Tab | 内容 |
|---|---|
| 计划 | 历史计划列表；没有计划时为空状态 |
| 行程 | 当前执行中的行程；没有则为空状态 |
| 提醒 | 通知 + 待办合并；按优先级排序 |
| 我的 | 用户名、成员 ID、服务器、定位权限、默认偏好、隐私说明 |

“方案”不再占 tab，改成 modal bottom sheet；“通知/待办”不再各占 tab，合并进“提醒”。

### 12.2 方案改为弹窗

- 触发：用户点“看改法”、天气弹窗、定位迟到弹窗、手动“模拟变化”。
- 形式：底部弹窗（BottomSheet）或全屏 Dialog。
- 内容：
  - 顶部：这次变化是什么（下雨/晚到/取消）；
  - 两张方案卡：A 保时间 / B 保体验；
  - 每张卡：保留率、改动数量、牺牲项、关键改动 1–2 条；
  - “查看全部改动”可展开；
  - 主按钮：`采用这个方案`；次按钮：`先不改`。
- 应用后关闭弹窗，回到行程页；不跳独立页面。

### 12.3 通知和待办不是两份：一个事件只产生一条行动项

**先纠正现在的重复**

当前流程是：

`应用方案 → 通知页（勾选谁要通知）→ 确认并生成待办 → 待办页`

同一件事被写了两遍：

- 通知页说“餐厅取消，要告诉同行”；
- 待办页又说“告知同行：餐厅取消”。

用户自然会问：“为啥要写两遍？你不会自己去通知，而是我去？”

**正确概念**

“通知”和“待办”不是两个列表，而是同一条行动项的两种执行方式：

| 执行方式 | 谁来做 | 例子 | 界面 |
|---|---|---|---|
| `auto` 自动 | 系统 | 通知同行程 App 内成员、更新活动记录、写系统日历 | 显示回执：“已通知 3 位同行” |
| `assist` 协助 | 你点一下 | 给餐厅打电话、把变更发给微信好友、复制话术 | 一条待办，带“拨号/分享/复制”按钮 |
| `info` 知会 | 不需要动作 | 谁改了什么、投票结果 | 折叠在“已发生”里 |

重点：

- 能自动的，系统直接做，不再让用户“确认通知对象”。
- 不能自动的，只保留一条“需要你做”的行动项，不再先有通知页、再生成待办页。
- 微信/电话受安卓限制，App 不能静默代发/代打；只能预填内容并打开分享/拨号界面，所以它们属于 `assist`，不是 `auto`。

**目标流程**

`应用方案 → 系统自动通知 App 内成员 + 生成一条行动项 → 提醒页`

提醒页只显示：

1. `已自动通知：3 位同行（刚刚）` —— 回执，不需要操作；
2. `需要你做：给「XXX 餐厅」打电话确认 14:30 到` —— 一条待办，按钮“拨号/复制话术/标记完成”；
3. `已发生：方案已应用到 v4` —— 只读记录。

如果以后接入推送/微信 SDK，能把 `assist` 升级成 `auto`，界面只改执行方式，不再新增一套“通知”页面。

**合并规则**

- 一个 `scheme` / 一次变化只生成一条行动项；
- `shift_all` 只生成一条“整体推迟 30 分钟”行动项；
- 同一节点同一类提醒不重复；
- 用户点“完成”后折叠到“已完成”，不再出现在主列表。

**验收标准**

- 应用方案后不再出现“确认并生成待办”这一步。
- 同一次变化在提醒页只出现一条，不会既有通知又有待办。
- App 内成员能自动收到；外部电话/微信显示为一条“需要你做”，带一键操作。
- 用户能清楚看到“哪些已自动完成、哪些还需要我”。

### 12.4 新增“我的”页

至少包含：

- 用户名 / 昵称（可改，影响到协作和投票显示）；
- 成员 ID（可复制，用于加入同一行程）；
- 服务器地址 + 连接状态 + “自动寻找/测试连接”；
- 定位权限状态 + 去系统设置；
- 默认偏好：节奏、通勤上限、是否少走路、默认兴趣；
- 通知设置：天气弹窗、迟到提醒、投票提醒；
- 数据与隐私：位置只用于当次判断、不存轨迹；
- 版本号、构建时间、诊断日志入口；
- 演示模式开关（示例计划、离线数据）。

设置对话框可以保留为“快速设置”，但主入口放到“我的”。

**验收标准**

- 底部只有 4 个 tab，不再有“方案/通知/待办”三个独立 tab。
- 需要改行程时，方案以弹窗出现；选完回行程页。
- 提醒页能区分“已自动完成 / 需要你做 / 已发生”，同一事件不重复。
- “我的”页能改用户名，重启后保留；能看到服务器和定位权限状态。
- 同一次整体推迟只出现一条待办。

**优先级**：P1

## 需要你拍板的 5 个决策

1. **底部导航**：建议 4 个（计划 / 行程 / 提醒 / 我的）。你是否接受把“方案/通知/待办”从 tab 里拿掉？
2. **城市必看池**：建议每城 8–12 个，按高德评分/类型选。你希望“必看”更多还是更少？
3. **单人投票**：建议单人时隐藏投票，改成“直接选方案”；多人时才显示投票。是否接受？
4. **起点通勤**：建议第一段最多放宽到 90 分钟，超过 90 仍保留起点但只排少量点；跨城 >80 km 才退回市区中心。是否接受？
5. **天气弹窗**：建议降雨概率 ≥60% 且命中户外点才弹，同一场雨只弹一次。阈值是否调整？

这 5 个决策确认后，再按批次动代码，避免改完又推翻。
